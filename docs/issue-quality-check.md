# 子Issue妥当性チェック基準

Nine標準AI開発フローでは、子IssueをGitHubへ登録する前に品質チェックを行う。

目的は、CodexがIssue単位で安全に実装でき、1 Issue = 1 PRでレビュー可能な状態にすること。

## 判定対象

各子Issueについて、以下の5項目を確認する。

### 1. 目的が1つに絞られているか

良いIssueは、達成したい目的が1つに明確化されている。

分割を検討する例：

- API追加とUI変更が同時に含まれている
- 新機能と大規模リファクタリングが混在している
- データモデル変更、認証、画面変更を1 Issueで扱っている

## 2. 変更範囲が予測できるか

実装前に、どのディレクトリ・モジュール・主要ファイルを触る可能性が高いか説明できること。

危険な兆候：

- 「必要なところを全部変更する」など範囲が無制限
- 多数の共通ファイルを横断する
- 他Issueと同じ重要ファイルを大きく変更する

この場合は分割、直列化、または設計Issueを先に作る。

## 3. 単独で完了判定・テストできるか

Issue単体で「できた / できていない」を判断できること。

最低限、以下のいずれかを示す。

- 自動テスト
- APIレスポンス確認
- UI動作確認
- build / lint / type check
- 明示された手動確認手順

テストを追加・更新・統合・削除するIssueでは、さらに以下を確認する。

- 検証したい責務に合ったテスト種別が選ばれているか
- Unit / Controller・API / Repository / Integration・E2E の役割が不必要に重複していないか
- 既存テストを削除する場合、そのテストが担っていた検証責務の移行先、重複、または不要になった理由が明記されているか
- 削除後も認証・認可、入力検証、Repository境界、重要な回帰テストなどの安全性確認が失われないか
- 重要なHappy Pathやシステム接続確認について、必要なIntegration / E2Eテストが安全網として残るか

「CIを速くしたい」「テストが重い」だけを理由に、検証責務の移行先を確認せずテストを削除してはいけない。

「全体が完成したら確認する」しかないIssueは、依存関係または分割方法を見直す。

## 4. 1 PRでレビュー可能か

レビュアーが1つの目的として理解できる変更量になっていること。

次の場合は分割を検討する。

- 複数の独立機能が入っている
- 変更理由が複数ある
- PRタイトルを1文で表現しにくい
- レビュー時に別々の観点で承認が必要

行数だけで機械的に判断せず、変更の意味的なまとまりを優先する。

## 5. 依存関係が明確か

他Issueに依存する場合は明記する。

例：

```text
Depends on #12
Blocked by #12
```

依存Issueが未完了の状態で安全に実装できない場合は直列化する。

独立していて変更ファイルも競合しない場合のみ並列実装候補とする。

# スコアリング

各項目を0〜2点で評価する。

- 2点: 明確で問題なし
- 1点: 実装可能だが曖昧さあり
- 0点: 分割・再設計が必要

合計10点満点。

## 判定

- 9〜10点: GitHub登録してよい
- 7〜8点: 軽微な修正後に登録
- 0〜6点: 原則として分割・統合・再設計する

ただし、以下のいずれかが0点なら合計点にかかわらず再検討する。

- 目的
- 完了判定 / テスト可能性
- 依存関係

# 分割するべきサイン

次のどれかに該当する場合は分割を優先する。

- タイトルに「〜と〜」が複数並ぶ
- 完了条件が異なる機能群に分かれている
- API、DB、UI、インフラを一度に大きく変更する
- 別々にロールバックしたくなる変更が混ざっている
- テスト方法が複数の独立機能に分かれる
- PRレビュー担当を分けたくなる

# 統合するべきサイン

細かくしすぎたIssueは統合する。

- 単独ではユーザー価値も技術的完了もない
- 数行の変更だけで別Issueにする意味が薄い
- 必ず同じPRで変更しなければ動作しない
- 完了条件・テスト・変更ファイルがほぼ同じ

# 子Issue作成前の標準工程

```text
計画書
  ↓
仮の子Issue作成
  ↓
5項目で妥当性評価
  ↓
分割 / 統合 / 依存関係修正
  ↓
9点以上を原則目標
  ↓
GitHubへ登録
  ↓
Codex実装
```

# ChatGPTがIssue化する際の標準ルール

「Nine標準AI開発フローでIssue化して」と依頼された場合、GitHubへ登録する前に各子Issueをこの基準で評価する。

問題があるIssueは、そのまま登録せず、分割・統合・依存関係の整理を行う。

各子Issueには原則として以下を含める。

- 目的
- 実装内容
- やらないこと
- 変更してよい範囲
- 原則変更しない範囲
- 完了条件
- テスト条件
- 依存Issue
- 並列実装可能かどうか

テスト削除を含むIssueでは、テスト条件に「削除対象が担っていた検証責務」と「削除後にその責務をどこで保証するか」を明記する。

最終目標は、CodexがIssue本文だけを読んでも作業範囲と終了条件を判断できる状態にすること。
